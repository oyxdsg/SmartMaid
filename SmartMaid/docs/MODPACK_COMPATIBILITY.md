# SmartMaid 整合包兼容性改善方案

> 目标：让 SmartMaid 能被整合包作者**放心地放进整合包**，并且在整合包环境里**开箱能用**。
> 本文是调研 + 体检 + 分期方案，**不含代码改动**。基线：`master` @ `07f0956`（2026-09-24，v0.1.0）。
> 编写日期：2026-09-28。最后更新：2026-09-28（应用三项决策）。
>
> **配套文档**：
> - [`MOD_COMPATIBILITY_ANALYSIS.md`](./MOD_COMPATIBILITY_ANALYSIS.md) —— 与其他模组的**冲突分析**（代码级证据、风险分级、实测清单）。若你只关心"会不会和别的 mod 打架"，直接看那一份。
> - [`IMPL_MODPACK_COMPAT.md`](./IMPL_MODPACK_COMPAT.md) —— **技术实现细化**（每个修复项落到 文件/API/代码骨架/坑/验证，API 签名均已用 `javap` 对真实 jar 核实）。要开工改代码时看这一份。

## 〇、结论先行

整合包收录的障碍**不在"功能不够"，而在三类完全不同的东西**，按优先级：

| 层级 | 问题 | 卡住的是 | 严重度 |
|---|---|---|---|
| **法律授权** | jar 里打包了 **CC BY-NC-SA 皮肤**（NC=禁商用）+ **GPL-3.0 表情**；商店图标是 **AI 生成**（Modrinth 明令禁止 AI 图标） | 平台审核 + 整合包作者的再分发顾虑 | 🔴 **阻塞**（方向已定，见下方决策） |
| **开箱可用** | 五个命令要 **GameMaster 权限**（单人整合包默认关作弊 → 玩家根本召唤不出女仆）；桥接**默认开启**（整合包里没桌宠 → 白写文件 + 空连 WS） | 玩家"装了发现没用" | 🔴 **阻塞** |
| **数据驱动** | 搭路建材是**硬编码黑名单** → 整合包里的贵重方块会被女仆当砖头用掉；战斗目标硬编码排除表 | 实际丢东西、行为不符合整合包预期 | 🟠 高 |
| **元数据** | 只在 GitHub 发布（CF/Modrinth 都没有项目）→ **整合包无法引用**；缺 `contact` / 版本约束 / 英文描述 / 变更日志 | 收录流程本身 | 🟠 高 |

**四条最重要的判断**：

1. **`/summonmaid` 需要 GM 权限是当前最致命的可用性问题。** 整合包玩家在单人存档里 `allow-cheats=false`，`/summonmaid` 会直接报权限不足 —— 而这是召唤女仆的**唯一入口**。这一点不修，整合包收录了也没人用得了。
2. **皮肤/表情的许可条款决定了收录范围。** CC BY-NC-SA 的 NC 条款与 CurseForge 的整合包收益计划（Reward Program）存在结构性冲突 —— **已决策：接受"只进非商业整合包"，走"保留 + 明确声明"路线**（详见下方决策记录）。代价是：凡有变现的整合包（含 CF Reward Program）都进不了，且必须在项目页面显著声明。
3. **上架平台是前置，不是后续。** CurseForge 规则明确：整合包里只能引用 **CF 上已批准**的 mod（非 CF 托管需进 Non-CurseForge Approved 白名单）；Modrinth 的 `.mrpack` 同理引用平台项目。现在只有一个 GitHub 仓库，整合包**在技术上就引用不了**。
4. **真正的冲突风险不在"改原版"，而在"内嵌库"和"绕过原版流程"。** 详见配套文档
   [`MOD_COMPATIBILITY_ANALYSIS.md`](./MOD_COMPATIBILITY_ANALYSIS.md)。

## 〇之二、已拍板决策（2026-09-28）

| 议题 | 决策 | 连带影响 |
|---|---|---|
| **皮肤（CC BY-NC-SA）** | **接受只进入非商业整合包**，不替换皮肤 | ① 项目页面/NOTICE 必须**显著声明"含 CC BY-NC-SA 素材，禁止用于商业整合包"**；② 主动排除 Any 变现型整合包（含 CurseForge Reward Program 相关）；③ 若日后想上推荐位/变现渠道，需重新评估 |
| **商店图标** | **确认由 AI 生成** | 🔴 **必须重画**（手绘或设计工具）—— Modrinth Content Rules §6.2.1 **明令禁止 AI 生成的图标/画廊图**；CurseForge 允许但要求**显著披露**。此项与是否商业无关，是硬规则 |
| **多女仆 / 持久化** | **暂不做** | 从 P2 范围移除；"每玩家一只 + 退出消失"保持为既定设计，不再作为收录阻塞项 |

> **仍未闭环的一项**：GPL-3.0 的 11 个表情 JSON 是"随 jar 分发"的 copyleft 素材。
> 它与"商业/非商业"无关 —— 约束的是**再分发时的义务**（须随附许可与源码）。
> 两种处理都可接受，取决于你对"整合包作者嫌麻烦而不收"的容忍度：
> - **保留**：NOTICE 已在 jar 内（`META-INF`），法律上可论证为"聚合分发"；但部分作者会主动规避带 GPL 素材的 mod。
> - **剥离**（推荐）：把表情移到独立可选包，主 jar 纯 MIT —— 收录阻力最小。
> 建议：**先按"保留"发布，观察是否有整合包作者因此犹豫再剥离**（成本可延后）。

## 一、调研依据（外部标准）

| 来源 | 关键约束（对本项目直接相关） |
|---|---|
| **Fabric Loader 文档** — [`fabric.mod.json`](https://docs.fabricmc.net/develop/loader/fabric-mod-json) | `environment` 决定物客户端/服务端加载（`client` 则专用服务器不加载）；`depends` / `recommends` / `suggests` / `breaks` / `conflicts` 五档依赖语义；嵌套 jar 由 `jars` 声明（Loom 的 `include` 自动填） |
| **Modrinth Content Rules**（更新于 2026-08-13） | §2.2 **描述必须有英文版**；§5.6 **所有依赖必须在 Dependencies 里声明**；§1.11 **未经明确披露不得向远程服务器上传数据**；§3 **自动 PvP 战斗须有服务端 opt-out 才不算作弊**；§6 **必须披露 AI 生成内容**，且 **§6.2.1 禁止 AI 生成的图标/画廊图**；§6.2.2 禁止整体由 AI 产出的项目公开发布 |
| **CurseForge Moderation Policies** | 整合包内所有 CF 托管的 mod **必须存在于 CF 且已批准**；文件必须带 **changelog**；菜单/画廊至少 1 张游戏内截图 |
| **CurseForge Project Distribution Toggle** | 作者可开关"允许第三方分发"（默认开）；需与许可证选择保持一致 |
| **CurseForge 整合包导出文档** | 整合包以 `manifest.json` **引用**平台项目，而非直接塞 jar（塞进去会被自动驳回） |
| **整合包分发模型**（社区共识 + 平台文档） | 客户端/服务端 mod 必须与整合包声明一致；只加方块/实体/维度的 mod 必须**双侧同版本**；纯客户端 mod 不能进服务端 |

**对"被收录"的推论**：整合包作者挑 mod 时看四件事 —— ① 平台上有项目且许可干净；② 默认配置下装了就能玩；③ 不会被玩家投诉"女仆把我钻石块用掉了"；④ 出问题能找到人（issue 链接）。本方案就是按这四条排的。

## 三、改善方案（分期）

### P0 — 授权声明与硬规则合规（阻塞项，必须先做）

**方向已定：不剥离 NC 皮肤，走"显式声明 + 限定收录范围"路线；但图标必须重画（与商业无关的硬规则）。**

1. **皮肤 —— 保留，但必须显式声明**（对应 A1）
   - `NOTICE.md` §3 已有完整署名链 → 补一句"**本素材为非商业（NC）授权，禁止用于任何商业性质的整合包/分发**"。
   - 项目页面显著位置加 "Non-commercial assets" 声明段（Modrinth / CurseForge 的项目描述里单列素材例外，避免误导审核与用户）。
   - 项目 license 字段保持 MIT，但描述中必须说明素材例外 —— 否则会被判为"元数据与实际不一致"。
   - 主动排除变现型整合包（含 CurseForge Reward Program）。这是已确认接受的取舍。
2. **图标 —— 必做**（对应 A3）
   - `docs/images/smartmaid-icon.png` **重画**（手绘 / 矢量工具）。
   - 同步检查 `docs/images/smartmaid-cover-240x150.png`（mcmod 封面）：若是 AI 生成同样要换。
   - 3 张游戏内截图是实机拍摄 → 无需处理。
3. **表情 —— 暂保留，可延后剥离**（对应 A2）
   - 维持现状：`NOTICE.md` 已在 jar 内 `META-INF`，构成"聚合分发"。
   - 若后续收到整合包作者反馈（"带 GPL 素材不收"），再按决策记录中的方案剥离为独立附加包。
   - **开包复验时记录现状**：jar 内含 11 个 GPL-3.0 文件 + 1 个 NC 皮肤，作为发布基线。
4. **披露与文案**（对应 A4、A5）
   - Modrinth 项目勾选 "Contains AI-generated content"（代码大量 AI 实现，规则 §6.1 要求）。
   - 补英文 README / 英文项目描述（§2.2）。
   - 描述中写明"桌宠为可选依赖""默认零副作用"。

**验收**：图标非 AI 产出；项目页面含非商业素材声明 + AI 披露；英文描述可读且与许可证字段不冲突。

### P1 — 上架与元数据（收录前置）

1. **上架 Modrinth + CurseForge**（双平台，缺一不可 —— CF 整合包只引用 CF 项目，`.mrpack` 只引用 Modrinth 项目）。
2. **补全 `fabric.mod.json`**：
   - `contact`: `homepage` / `sources` / `issues`
   - `depends.fabric-api`：`">=0.158.0+26.2"` 之类具体下限，去掉 `*`
   - `suggests`: 桌宠联动（说明"可选，不装也有完整规则引擎"）
   - `recommends`: `modmenu`（若做配置界面）
   - 确认 `environment` 与实际一致（当前 `*`，正确）
3. **`CHANGELOG.md`**（按版本）+ 平台版本说明。
4. **页面素材**：至少 1 张游戏内截图（已有 3 张 ✅）、清晰的依赖说明（Fabric API 必需、桌宠可选）。
5. **README 增"整合包作者须知"段**：见附录模板。

**验收**：CF/Modrinth 项目可被整合包工具检索并成功解析依赖。

---

### P2 — 开箱可用（整合包玩家体验）

1. **命令权限**（对应 B1，最高优先）
   - 主推：可配置权限等级（config 项，默认 **`LEVEL_ALL`** 或"仅拥有女仆的玩家可用"），或
   - 备选：`/summonmaid` 降到默认可用，其余调试命令保持 GM 级。
   - 目标：**单人整合包不开作弊也能召唤**。
2. **桥接默认关闭 / 自动探测**（对应 B2、B3）
   - `BridgeConfig` 默认 `enabled=false`、`ws.enabled=false`；或首次启动检测桌宠目录/端口存在才启用。
   - WS 客户端加环境判断：**专用服务器跳过**。
   - 遥测目录默认不落在服务器根目录。
3. **引入主配置文件**（对应 B4、B6）
   - 统一 `config/smartmaid/main.json`（或 TOML）暴露：跟随距离档位、护主模式默认值、战斗目标白/黑名单、桥接开关、感知采样间隔、性能档位。
   - 强烈建议接 **ModMenu**（整合包玩家 99% 用 ModMenu 改配置）。
4. **不改玩法，只加开关**：B5（唯一女仆、退出消失）**已决策暂不做改动**，保持既定设计；但它不再是收录阻塞项 —— 玩家侧体验可用文档说明清楚。

**验收**：干净环境（无桌宠、无作弊）装包 → 能召唤、能跟随、能战斗、无多余文件写入、日志无异常。

### P3 — 数据驱动（深度兼容）

1. **建材消耗改为白名单 tag 驱动**（对应 C1，最实用）
   - 定义 `#smartmaid:bridge_blocks`（数据包可覆盖），默认内容 = 原版 `#minecraft:dirt` / `#c:cobblestones` / `#c:stones` 之类**便宜方块**；
   - 逻辑反转：**只有白名单内的方块才允许消耗**（现在反了：只有黑名单外才允许）。这样整合包的新贵重方块默认安全。
   - 保留 config 追加黑名单。
2. **`bridgePriority` 改 tag 驱动**（对应 C2）。
3. **战斗目标**支持 `EntityTypeTags` 排除/白名单 + config（对应 C3）。
4. 把所有"魔法数字"（战斗死区 2.7~3.2、攻击距离 3.2、感知半径、任务超时）搬进 config，并写默认值注释。
5. 新增 `data/smartmaid/tags/` 供数据包覆盖（整合包作者最喜欢的接口）。

**验收**：用整合包特有方块做测试 —— 女仆不会消耗它；数据包能覆盖行为。

### P4 — 性能与共存（整合包 TPS 敏感）

1. 审计每 tick 开销：战斗 Goal 判定、感知采样（默认 750ms）、寻路 A\*、结构扫描。
2. 提供"轻量模式"配置（拉长感知间隔 / 降低扫描半径）。
3. 写明与常见优化 mod（Lithium / Sodium / FerriteCore）的共存情况 —— **SmartMaid 自身无 mixin**，对优化类 mod 的冲突面极小；
   但要注意**内嵌的 PAL 携带 14 个 client mixin**（目标为 `LivingEntityRenderer` / `ItemInHandLayer` / `PlayerModel` / `firstPerson.*` 等原版渲染类），
   与 EMF / Fresh Animations / First Person Model 等视觉 mod 有重叠面。完整证据与实测清单见
   [`MOD_COMPATIBILITY_ANALYSIS.md`](./MOD_COMPATIBILITY_ANALYSIS.md) §2。
4. 日志已默认静默（`MaidDebug.ENABLED=false`，`MaidDebug.java:20`）✅ 保持。
